生日祝福页逻辑笔记

发表于2026-08-24|更新于2026-11-08|学习前端
|浏览量:

对应文件：script.js（主逻辑）、cake3d.js（3D 背景）

这一篇按「一局祝福从打开页面到收下全部」的顺序，把两份代码摊开讲：先说页面有哪些状态、坐标怎么算，再说卡片怎么排、怎么建、怎么调度，最后说音乐、3D 背景和加载性能。读法和本系列的小游戏笔记一样——每段先给结论，再摊开代码逐行说「为什么这么写」，最后讲边界和取舍；文中标了源码文件与函数名的链接，点开可以对照着看。

一、这个页面是什么

同一个页面有两种身份，打开时按日期自动切换：

生日季（8 月 20–25 日） 平时
标题 生日快乐 今天也要好好的
卡片内容 生日祝福语（约 124 条池子） 每日鼓励语（约 64 条池子）
3D 背景 生日蛋糕（cake 场景） 星空（star 场景）

为什么这么设计：这个页面一年只用 6 天可惜了，平时当作”每日小鼓励”页，生日季自动变身，一套代码两份价值。

把一次访问拆成数据流看，会发现「两套身份」其实只由一个布尔值 isBirthday 派生：

这样写的好处是分支只有一处：判断写在第四节，其余代码只读 isBirthday 或 ACTIVE_WISHES，不必在每段里重复问「今天是不是生日季」。若散落成十几个 if (now.getMonth()===7 ...)，改一次日期区间要翻遍全文件，而且页面跨过零点时各处判断还可能给出不同答案。

为什么不做成两个页面：两套 HTML 意味着两套卡片逻辑、两套图片预加载、两套音乐解锁都要各维护一份，改一个动画得改两遍；而且站点上多一份文件就多一份缓存失效的成本。这里两份身份共用同一套流程，只换「数据」和「场景参数」，是同一份代码的两个输入。

路径为什么这样写：index.html 里引用的是 style.css、script.js 这种不带斜杠的相对路径，浏览器会按「当前页面所在目录」拼成 /birthday/style.css；script.js 里的 img/imageN.jpg、./cake3d.js 同理，也相对 /birthday/ 解析。所以整份代码可以整目录搬到任何位置，不用改一行路径——这正是 Birthday/ 独立单页版能直接双击打开的原因。本文里写的 /birthday/script.js 是从站点根目录出发的绝对路径，只用于笔记里的链接，和代码里的相对路径不是一回事，别混了。

index.html 顶部 front-matter 里的 layout: false 也别删：它告诉 Hexo「这页不要套主题的页眉页脚和侧栏，原样输出」。少了它，生日页会被塞进博客的文章模板，固定设计稿缩放（第六节）就全乱了。

依赖是单向的：index.html → script.js →（运行时）cake3d.js → js/three.module.js。script.js 完全不知道 three.js 的存在，只调一个 mount()；反过来 cake3d.js 也不碰卡片 DOM，只往传进来的容器里画。两边通过「一个容器元素 + 一个 scene 字符串」通信，这是第十二节说的隔离能成立的前提。

三、为什么代码包在 (function(){...})() 里

script.js:1

这是 Immediately Invoked Function Expression（立即执行函数）。原因：hexo 博客的每个页面共用同一个浏览器全局环境，主题脚本、搜索脚本都会定义全局变量。如果这里直接写 var naturalW = 0，万一主题里也有个 naturalW，谁后加载谁覆盖谁，会出现”别的页面坏了”这种很难查的 bug。包一层后，这里所有变量都是函数内部的私有变量，外面看不见，从根上避免冲突。

把文件的首尾对着看，形状是这样：

  • (function(){ ... })：把函数体整个包进圆括号，圆括号里的内容会被当成表达式而不是函数声明，所以后面能直接跟 () 调用；
  • 末尾 ()：立刻执行，且只执行一次。整个文件没有一句代码留在全局作用域里执行；
  • 里面所有 var 都是这个函数的局部变量。函数执行完按理该消失，但因为事件回调（click、resize、error）还引用着它们，这些变量随闭包一直活着，成为这一页的「状态」——相当于一个没有打包成对象的状态集，和小游戏笔记里把一整局塞进 S / G / M 是同一件事的两种写法。

顺手把这份「散装状态」列成表，读后面各节时可以回来对照：

变量 记的是什么 谁改它
naturalW / naturalH 设计稿画布的宽高，恒为 2560 / 1440 updateScale()
isBirthday / ACTIVE_WISHES 本局身份与选中的文案池 开局算一次，之后只读
heartPositions / heartDelays / heartRainfall 本局心形点位、出现节奏、是否落体 generateHeartPositions()、resize

为什么不用 <script type="module">：模块作用域确实也能隔离变量，但模块脚本默认 defer 且受 CORS 限制，用 file:// 直接双击打开独立单页版时会被浏览器拦下。IIFE 是最老也最不挑环境的隔离办法，兼容到十年前的浏览器；而且这份代码全是 ES5 写法（var、function），正是为了在任何环境都能跑。代价是没有 const、箭头函数、顶层 await，写起来啰嗦一点——第十节那个循环里额外包一层 IIFE 就是为了补 var 没有块级作用域的坑。

一个容易忽略的边界：IIFE 只隔离变量，不隔离 DOM。若主题脚本也去取 #startBtn 这种 id，照样会撞上。所以这里的 id 都用了完整业务名称，且唯一的全局入口就是 index.html 里那十几个元素。

四、两套祝福语池 + 日期判断

  • isBirthdaySeason()（script.js:198）：拿当前日期和上面的区间比对，返回 true/false。只判断一次，结果存在 isBirthday 里，之后整个页面都用这个结果。
  • ACTIVE_WISHES = isBirthday ? BIRTHDAY_WISHES : DAILY_WISHES：选出本次要用的文案池，后面所有卡片都从这里随机抽。

意义：判断逻辑只写一处，生日当月改日期区间就能调整”生日季”，其他代码一行不用动。

为什么文案直接写死在代码里：站点部署在 GitHub Pages 上，是纯静态托管，没有服务器和数据库，文案只能放前端。纯静态是这类个人博客的常态。

把判断函数摊开看，一共四行：

  • new Date() 不带参数就是「此刻」，读的是浏览器所在机器的本地时间，不是服务器时间、也不是 UTC。纯静态站点没有服务端可问，只能这样；好处是访客在自己时区的 8 月 24 日打开就是生日版，坏处是东西半球差一天，跨零点时可能和博主所在地不一致——对一页祝福页来说可以接受；
  • getMonth() 返回 0~11，所以 8 月写成 7。这是 JS 最经典的差一错误，第十六节速查表里专门标了「月份记得减 1」；
  • 两个 >= / <= 是闭区间，20 号和 25 号都算，一共 6 天，正好对上第一节表格里的「8 月 20–25 日」；写成 < DAY_END 会少一天；
  • && 短路：月份不对时后面两个比较根本不会算。这里省不了多少，但「先写最便宜、最能排除的判断」是写条件表达式的习惯。

var isBirthday = isBirthdaySeason(); 在模块初始化时只算一次。这意味着页面开着跨过午夜 12 点，身份也不会中途跳变——欢迎窗是生日版、卡片却是平日版这种撕裂状态不会出现。想让它实时响应，得挂定时器每分钟重算并同步改文案池和 3D 场景，收益极小、复杂度陡增，不值得。

ACTIVE_WISHES 拿到的是其中一个数组的引用，不是复制一份。两个文案池加起来不到两百条字符串，复制也不贵，但引用更直接：后面 randomFrom(ACTIVE_WISHES) 每抽一张卡都读它，读写都走同一个入口。

为什么用数组 + 随机，而不是按顺序轮播：顺序轮播意味着每次打开都是同一句开场白，第三次访问就腻了；随机抽取让 124 条（或 64 条）文案在 3048 张卡片里组合出几乎不重样的排布。代价是同一屏里偶尔会抽到重复的两句——池子比卡片数大 24 倍，重复概率不高，且祝福语重复并不刺眼，属于可以接受的取舍。真要彻底不重复，得先洗牌再按序取（第八节那套 Fisher-Yates 就能复用），多维护一个索引而已。

五、卡片数量与尺寸常量

script.js:219-226

数量计算在 tipCount()（script.js:295）：屏幕宽 × 高 ÷ 16000，再被 min/max 夹住。

  • 为什么按面积算：屏幕大就多放、屏幕小就少放，心形的”密度感”在任何设备上接近。
  • 为什么有下限：之前下限是 14，小窗口打开时心形稀稀拉拉（你反馈的”距离太大、数量少”就是这个），2026-11-07 调成 30/64，2026-11-08 又因”心形被塞太满、重叠成团看不出形状”把上限收到 48。

把计算摊开：

  • Math.round 先取整，卡片数必须是整数；用 floor 也行，只是同尺寸下少一张，视觉无差别；
  • Math.min(TIP_MAX, n) 先压上限，再 Math.max(TIP_MIN, …) 抬下限。两个夹子合起来就是常见的 clamp 写法；先夹哪一头在这里结果相同，但「先夹上界再夹下界」的写法在改常量时更不容易踩坑；
  • 代几个真实尺寸：1280×800 → 1024000/16000 = 64 → 48；1920×1080 → 129.6 → 130 → 48；手机 390×844 → 20.6 → 21 → 30，被下限抬到 30。也就是说绝大多数桌面屏拿满 48 张，绝大多数手机拿 30 张，中间段（约 640×750 到 1280×800）才真正体现「按面积算」。

上限 48 不只是怕 DOM 多、动画卡：心形采样是 t = i × 2π/count，点数越多相邻两点越近，卡片会大面积重叠成一坨，反而看不出心形。所以 TIP_MAX 同时也是视觉上限。

这些常量集中写在文件顶部一段（script.js:219-226），是刻意安排的：调密度只改 TIP_AREA，调节奏只改 TIP_INTERVAL，调大小只改 WISH_W / WISH_H_MIN，不用翻到算法里找魔数。第十六节的速查表就是这段常量的「人类可读版」。改 WISH_W 时，心形采样的 availableW 会自动跟着减（第七节），但 style.css 里卡片的 CSS 宽度要手动同步，这是全文最容易漏改的一处。

六、（旧方案，已废弃）固定设计稿 2560×1440 + 整体缩放

2026-11-08 已改造为真实视口自适应：updateViewport() 直接用真实视口当坐标系，不再整体缩放；所有 UI 尺寸由统一比例系数 --s = clamp(0.60 × (短边/1080)^0.55, 0.40, 0.72) 派生（桌面卡片约 162px、手机约 108px），文字与触摸目标有 px 下限保证看得清点得到。横屏心形等比、竖屏最多纵向拉伸 1.6 倍，坐标经 toScreen() 夹在视口内；resize / orientationchange / visualViewport.resize 防抖重排并沿用当前动画模式。卡片已去掉「收下」按钮，只留图片和文字，高度随文案变化，创建时用 offsetHeight 实测、wishTop() 把中心重新对齐到心形点位。以下为改造前的实现记录。

script.js:278 updateScale()

写法：卡片坐标不是按你的屏幕尺寸算的，而是在一张虚拟的 2560×1440 “画布”（overlayLayer）上算，然后用 transform: scale() 把整张画布等比缩放到刚好装进真实窗口。

为什么这么写：

  1. 心形位置、卡片大小只需按一套坐标写死，不用为每种手机/电脑分辨率单独适配；
  2. 任何屏幕上，心形相对屏幕的比例、卡片之间的疏密关系完全一致；
  3. 窗口大小变化（resize 事件）时只需重算一个缩放值，而不是重算几十张卡片的位置。

scale = min(窗口宽/2560, 窗口高/1440)：取小的那个，保证画布完整显示、上下或左右不留裁剪。

代码比公式多做了两件事：

  • if (!vw || !vh) return：某些浏览器在页面刚创建、或窗口被最小化时会给出 0，除下去会得到 0 或 Infinity，先把这种输入挡掉；
  • 两层各自的角色：bgContainer 被设成「缩放后的真实像素尺寸」，负责在页面里占对位置；overlayLayer 始终保持 2560×1440 的设计稿尺寸，只对它施加 transform: scale()。所以所有卡片坐标都以设计稿单位写，从不考虑真实屏幕——这正是这套写法省事的地方；
  • transform 缩放不改变元素的布局尺寸，只改视觉呈现，配合 transform-origin 才能按预期收缩；这也是为什么还要手动给 bgContainer 写像素宽高，否则外层盒子会按 2560 去撑开页面，出现横向滚动条；
  • 取 min 而非 max：取大的那个会把短边撑出视口，心形尖端被裁掉。取小的保证完整可见，代价是长边那一侧留出空白——1280×800 的窗口，scale = min(0.5, 0.555…) = 0.5，画布显示成 1280×720，上下各留 40px；深蓝背景会把这点留白吃掉，看不出来。

为什么不用响应式断点或百分比坐标：心形轮廓是数学公式算出来的点，任何「按屏幕百分比摆」的方案都得为不同宽高比重算一遍，而 2560×1440 是一张固定的虚拟画布，公式、卡片尺寸、留白都只有一套数字。窗口变化时 resize 回调只重算一个 scale，再按新画布重采样心形点（第十五节），不必重写任何坐标常量。

一个隐含约束：因为所有坐标都是设计稿单位，WISH_W = 270 指的是「画布上的 270」，在 1280 宽的屏幕上实际只有 135 CSS 像素。调卡片大小时要在设计稿尺度上想，别拿真实像素去估。

七、心形曲线公式（整个布局的数学核心）

script.js:323 sampleHeartPoints()

这是什么：经典的”心形参数方程”。参数 t 从 0 转到 2π，每个 t 算出一个 (x, y)，连起来就是心形轮廓。t 的步长 = 2π ÷ 卡片数，所以想要多少个点都行，且沿轮廓等弧度分布——不用手工摆 30 多个点位，改一个数量参数就能重排整颗心。

坐标范围推导（决定后面所有缩放）：

  • x 方向：sin³t 最大是 1，所以 x ∈ [−16, +16]，宽 32；
  • y 方向（数学坐标，y 朝上）：t=0 时 y = 13−5−2−1 = +5（两瓣之间的凹口），t=π 时 y = −13−5+2−1 = −17（下尖端），瓣顶最高约 +12——整个心形高约 29；
  • 代码整体取负号：屏幕坐标 y 是朝下长的，负号把心形”翻”成正立（两瓣在上、尖朝下）。

从公式坐标到屏幕坐标的换算（script.js:326-347）：

  1. base = min(可用宽÷32, 可用高÷32)（script.js:332）：公式宽 32，除以 32 就把心形刚好缩放进可用区域；宽高各算一次取小的，保证两个方向都不出界。可用区域 = 画布 − 左右各 20px 留白 − 卡片自身尺寸（先把卡片占的地方扣掉）。高度方向实际只需除 29，统一除 32 是”宁可略小、绝不越界”的简化，视觉无差别。
  2. − 卡片宽/2 / − 卡片高/2：算出来的点当卡片中心用，减半张卡片换算成左上角——CSS 的 left/top 定位基准是左上角。
  3. 横屏/桌面再横向放宽：sx = min(可用宽÷32, base × 1.3)、sy = base。宽屏上只按高度缩放会让心被压在中间、两侧空一大片（显得很小很不协调），所以横向最多放宽到 1.3 倍把多余宽度用起来，心更大更饱满；竖屏则保持 sx = base、sy = min(base × 1.6, 可用高÷32) 纵向拉伸。
  4. 不再整体下移：cy = 画布高 ÷ 2 + (顶预留 − 底预留) ÷ 2，直接以视口中线为基准。旧版有 −画布高 × 15% 的偏移，本意是视觉居中，实际会把心形顶部挤出安全区、被 toScreen() 裁切压平，反而看不出心形——这是 2026-11-08 修掉的主要 bug。手机端靠 topReserve（顶部工具栏 68px）的预留把心下移一点，避开工具栏。
  5. Math.max(5, …)：最后兜底，任何卡片离屏幕边缘至少 5px。

去重逻辑（目前关着，故意的）：dedup 开启时先按”离形状中心的距离”排序，再两两比对，距离小于 min(270,120) × 35% = 42（设计稿像素）的丢弃（script.js:360-381）。这是 O(n²) 的朴素算法——最多 64 个点，平方也才 4096 次比较，不值得上更聪明的数据结构。目前 8 个模式全部传 dedup=false：卡片适度重叠才有”堆满一屏”的密度感，完全不让重叠反而显得稀疏（踩过的坑）。

参数方程和隐式方程的区别：心形也可以写成一个 f(x,y)=0 的隐式方程（例如 (x²+y²−1)³ − x²y³ = 0），但要沿轮廓均匀取 30 个点，得先解出边界、再按弧长重采样，很麻烦。参数方程直接给「走一圈的路径」：t 从 0 到 2π 就是沿轮廓走一整圈，把这一圈等分成 count 份就得到 count 个点。公式里 cos t、cos 2t、cos 3t、cos 4t 是几个不同频率的谐波叠加——正是它们把单纯的椭圆「捏」出上面的两个瓣和下面的尖；16·sin³t 负责左右对称且让左右边缘饱满。

为什么 t 等分不等于弧长等分：参数走匀速时，曲线弯得急的地方点会密、平缓处点会疏。心形在尖端和凹口曲率大，那里卡片会挤一点。要严格按弧长均匀，得先算累积弧长再做反查表；这里没做，因为卡片本身有宽度、允许重叠，几十像素的疏密差肉眼看不出来，而弧长采样会多出一倍代码。能省的算法就省，把复杂度花在看得见的地方，和上面去重那段 O(n²) 的判断是同一个取舍。

换一种做法行不行：手工摆 30 多个点位当然可以，但数量一变（第五节按屏幕面积算 30~64）就要重摆一遍；用 CSS clip-path 或 SVG 路径也只能画形状，放不进几十个带图片和按钮的独立 DOM。参数方程是「一个数量参数决定整颗心」最经济的写法。

读代码时的两个小坑：sampleHeartPoints() 开头会调一次 updateScale() 重新取 naturalW/naturalH，所以采样永远基于当前设计稿状态，不会用到上一次窗口的旧值；返回的每个点带 dist（到中心的距离），只在去重开启时用于排序，dedup === false 时会被剥掉 dist 只留 {x, y}——返回结构随参数变化，这是为了不让下游拿到用不到的字段，也提醒读代码的人两种分支并不完全对称。

八、8 种心形布局模式：每次打开不重样

script.js:300 generateHeartPositions() 每次随机挑一种。点数相同，区别只在出现顺序和节奏：

模式 效果 为什么这么设计
growth 沿轮廓顺序出现 像一笔画爱心
random 位置铺满轮廓，出现顺序随机 铺开感，不呆板
curve_cw / curve_ccw 沿轮廓顺/逆时针依次点亮 有”描边”的仪式感
ripple 按离中心距离分 4 圈，从内到外荡开，每圈内乱序（间隔 260ms） 像涟漪扩散
heartbeat 位置随机，节奏 150ms-150ms-500ms 循环 模拟心跳”咚、咚、——“
outline_fill 40% 先描边（间隔 200ms），描完再随机向内部填充（间隔 500ms） 先画空心爱心再填满，层次最丰富
rainfall 位置随机，每张卡从上方 0.3 屏高处落下就位 卡片雨，动感最强

共同的返回格式：每个模式返回 { positions, delays }，delays[i] 是第 i 张卡出现的毫秒数；delays = null 表示”没有特殊节奏”，调度器就用统一的 300ms 间隔（script.js:826 的兜底 idx * TIP_INTERVAL）。把”在哪里”（positions）和”什么时候”（delays）分开返回，总调度函数就不用关心每个模式的动画细节——加新模式只要多写一个生成函数。

逐个拆开看算法：

growth / curve_cw / curve_ccw（script.js:384、399、430）
三个是同一份心形采样的三种”读法”：位置完全一样（都按 t = i × 步长 沿轮廓取点），curve_ccw 用 t = 2π − i × 步长 反着走一遍。delays 全是 null → 300ms 匀速。growth 和 curve_cw 的位置代码是重复的两份——两个才 30 行的小函数，抽成”带方向参数”的公共函数反而多一层绕，小重复优于早抽象。

random（script.js:388）：轮廓点取完后 Fisher-Yates 洗牌，再 300ms 匀速弹出。

ripple（script.js:461）分六步：

  1. 取心形轮廓点；
  2. 算每个点到”抬高后的中心”的距离（中心 y 同样 −15%，和心形对齐，否则涟漪圆心和心错位）；
  3. 按距离升序排序；
  4. 距离区间四等分切成 4 圈：第 r 圈 = [r × maxDist/4, (r+1) × maxDist/4)；
  5. 每圈内部 Fisher-Yates 乱序；
  6. 四圈首尾相接排成一列，延迟逐个 +260ms 累加。

效果：先内圈后外圈荡开，同圈内先后随机——像水波，但不是死板的同心圆。

heartbeat（script.js:508）：位置洗牌后，延迟是 [150, 150, 500] 循环的累加和——“咚、咚、——停顿”。30 张卡总时长 = 10 组 × 800ms = 8 秒，64 张约 17 秒。

outline_fill（script.js:532）：

  1. 40% 的卡（floor(count × 0.4)）放在轮廓上（心形采样，步长改成 2π ÷ 轮廓数），每张间隔 200ms，先把空心爱心描完；
  2. 描完停 300ms，剩下 60% 往内部填：随机角度 + 随机比例 frac（0 ~ 0.85），x = 16 × cos(角度) × frac，y 用心形公式在同样角度的函数值 × frac——相当于把整颗心形”向心压扁”后撒点，内部点会跟着心形轮廓的形状走，而不是撒成一个圆盘；frac 上限 0.85 是防止内部点戳出轮廓外；
  3. 填充每张间隔 500ms，比描边慢一倍多——先看清是颗心，再慢慢被填满。

一个遗留细节：填充循环里算了 rawY 但最终用的是 heartY，rawY 是没用上的死变量（script.js:565），读到别疑惑。

rainfall（script.js:587）：位置洗牌 + 300ms 匀速，但每张卡创建时先被放在”目标位置上方 max(0.3 屏, 200px)”处，并换一条专属 CSS 过渡（top 0.6s cubic-bezier(0.23,1,0.32,1)，急出缓停的落体手感），下一帧把 top 改成目标值——CSS transition 自动补间出”落下”动画。因为要先渲染一帧初始位置再改，这里用了两层嵌套 requestAnimationFrame（script.js:799-808），普通模式只要一层。

洗牌为什么用 Fisher-Yates（script.js:390）：从最后一个元素往前，每个位置和”它前面（含自己）随机一个”交换，n 个元素 n−1 次交换、O(n)，每种排列等概率出现。老写法 sort(() => Math.random() - 0.5) 看似随机，实际分布有偏且结果依赖浏览器排序实现——数组洗牌一律用 Fisher-Yates。

模式是怎么选的（script.js:300）：八个常量排成 modes 数组，modes[Math.floor(Math.random() * modes.length)] 等概率抽一个，再用一串 if/else if 派到对应的生成函数。没有用 switch、也没用「函数名映射表」，因为八个分支里有的要额外返回 rainfall: true 和落体距离，返回值形状不统一，写成表反而要塞特例。分支少、形状不齐时，直白的 if 链最好读。

顺着把返回值的完整契约补全：除了 { positions, delays }，rainfall 还会多带 rainfall: true 与 rainfallFallDistance，调度器（第十节）把它存进 heartRainfall / heartRainfallDistance，建卡片时才知道要不要先放到上方、过渡用哪条曲线。这类「可选字段」用 || false / || 0 兜底读取，没给的字段自动取默认值，新增模式不必回来改所有旧模式。

delays 是累加和还是绝对时间：是绝对时间——heartDelays[i] 直接交给 setTimeout(..., delay)，表示「从开始算起第 i 张在第几毫秒出现」。代码里各模式用 delay += interval 一路累加生成，所以数组单调递增；这里若误写成每次嵌套 setTimeout、把 interval 当成相对上一位的间隔，节奏会越走越慢（每张都等前面那张再加 interval）。delays = null 时退化的 idx * TIP_INTERVAL 同样是绝对时间，两种写法在调度器里才对得上。

怎么加第九种模式：① 加一个 MODE_XXX 常量并放进 modes 数组；② 写一个返回 {positions, delays} 的函数，位置仍从 sampleHeartPoints(count, false) 取，别自己造坐标，否则缩放和去重规则会不一致；③ 在 generateHeartPositions 的 if 链里加一支。调度器、卡片创建、resize 三处都不用动——这就是把「在哪里」和「什么时候」分开返回换来的扩展性。

为什么不用 CSS animation-delay 一次把 64 张卡全建好：那样 DOM 一开始就全在，浏览器要同时维护 64 个图层和 64 段动画，首屏内存和合成开销都上去了；现在的写法是「到点才建 DOM」，任意时刻场上只有已出现的卡片。代价是 64 个 setTimeout 要管，于是有了第十节那套 timeouts 数组。

九、卡片是怎么创建的

script.js:743 createRandomTipWindow(index)

每张卡片纯 JS 创建，由四样东西组成：

  1. 随机配图：从 21 张图里随机挑一张 img/imageN.jpg；
  2. 随机文案：从当前文案池随机抽一条；
  3. 随机底色：10 种半透明深蓝紫色调（TIP_BG_COLORS，透明度 0.72 左右——太实会挡住 3D 背景，太透文字看不清，0.72 是试出来的平衡值）；
  4. “收下”按钮：点击后 300ms 淡出再从 DOM 移除。

几个值得注意的细节：

  • wishImage.onerror = 隐藏图片：图片万一加载失败，卡片只剩文字照样能用，不会出现一个破图图标（兜底逻辑，成本一行）。
  • 位置 heartPositions[index % heartPositions.length]：取余是防御——万一某模式去重后返回的点比卡片数少，也不会取到 undefined。
  • 落下动画：rainfall 模式先把卡片放到”目标位置上方 0.3 屏”，下一帧再改回目标位置，靠 CSS transition 产生下落感（算法见第八节）。
  • 入场时机：普通模式一层 requestAnimationFrame，rainfall 两层（script.js:799）——必须等浏览器先完成一帧布局，再添加 visible 类（或改 top），过渡动画才会生效。直接加类的话浏览器会把”初始状态+动画状态”合并成一帧，卡片就没有入场动画了——这是前端动画的经典坑。

把创建过程按执行顺序摊开（script.js:743）：

  • style.setProperty('--card-tint', bgColor) 把随机底色写进 CSS 自定义属性，样式表里只管 background: var(--card-tint)。颜色有 10 种却不用写 10 个 class，改配色也只动 TIP_BG_COLORS 数组；
  • textContent 而不是 innerHTML：文案是硬编码字符串，本来没有注入风险，但用 textContent 是习惯——它把内容当纯文本，万一以后文案里出现 <3 之类的符号也不会被当成标签解析；第十五节 applySeasonCopy() 拼两行问候语时用的是 createTextNode + <br>，同一个道理；
  • wishImage.onerror 里 this 是那张 <img>，直接 display:none，卡片自动缩成「只有文字 + 按钮」，不会出现裂图图标。这是一行成本的降级；
  • 三个 appendChild 的顺序就是视觉叠放顺序：图上、文字中、按钮下，和本节截图里看到的一致；
  • 「收下」按钮的回调里先改 opacity 和 transform: scale(0.8)，300ms 后才 remove() 并把它从 wishElements 里 filter 掉。动画期间元素还在数组里，若此时点「收下全部」，closeAllWindows() 会把它再淡出一次——重复操作是安全的，因为 remove() 调两次不会报错，数组 filter 也是幂等的。

为什么每张卡片是独立 DOM，而不是一整块 canvas 画出来：卡片里有图片、文字、可点按钮，还要各自淡入淡出和单独被「收下」。用 DOM 这些全是浏览器现成能力（事件、过渡、焦点）；换成 canvas 得自己实现命中检测、文字排版和焦点管理，成本不成比例。3D 背景用 canvas 恰恰相反——那里只有点，没有交互元素，所以两种技术各用在了合适的一侧（见第十三节）。

heartPositions[index % heartPositions.length] 的取余还有一层含义：index 是第几张卡，heartPositions 是这一局的点位表，两者数量本来相等；取余只是在 resize 提前重算、或未来某个模式去重后点数变少时，兜住「点不够」的情况，避免读到 undefined.x 直接抛错。

十、总调度：startTipWindows

script.js:811

delay 取值规则（script.js:826）：模式给了 delays 就用 delays[i]，没给（null）就退回 i × 300ms 匀速。

为什么要把定时器都记下来：用户可能刚点开就点”收下全部”。closeAllWindows()（script.js:701）会把所有未触发的 setTimeout 全部取消（clearTimeout），并设 isClosing = true 作为双保险——即使某个 setTimeout 恰好已进入回调，回调开头的 if (isClosing) return 也会拦住。意义：没有这套机制，关掉页面后卡片还会陆续冒出来——“幽灵卡片”。

把调度器摊开（script.js:811）：

  • 开头几行是界面状态复位：按钮亮起、音乐按钮同步、3D 背景挂载，然后才算点位。把「挂载」放在算点位之前，是因为 3D 是异步 import，先发起请求能和后面的计算并行；
  • (function(idx){ ... })(i) 是个 IIFE，和第三节那个大 IIFE 是同一手法，但目的不同：这里为了给每一次循环造一份独立的 idx。若直接用 var i，64 个回调全都闭包到同一个 i，执行时读到的都是循环结束后的 count，所有卡片会挤在同一个点位上。这是 var 没有块级作用域的经典坑，用 let i 也能解，但这份代码整体是 ES5 风格，就统一用 IIFE；
  • heartDelays[idx] || idx * TIP_INTERVAL：|| 顺便兜住 delays 数组比卡片数短的情况（某个模式少给了一个延迟），退回匀速，不会变成 undefined 让 setTimeout 当成 0；
  • setTimeout 的延迟是从排队的那一刻算起的，不是「上一张出现后再等 delay」。所以 64 张 × 300ms ≈ 19 秒铺完；heartbeat 模式按累加和排，总时长由最后一个 delays 决定，第八节算过约 17 秒。

为什么 clearTimeout 之外还要 isClosing：定时器回调一旦被压进事件队列，clearTimeout 就拦不住了——它只能取消「还没到点」的，取消不了「已经到点、正排队等执行」的。closeAllWindows() 先置 isClosing = true，再清空数组并逐个 clearTimeout；调度器回调开头和 createRandomTipWindow() 开头各有一次 if (isClosing) return，两道门把竞态窗口堵死。状态标志 + 资源清理这套组合，但凡有异步任务可取消都该这么写。

restartWishes() 是它的镜像：把 isClosing 置回 false、userMuted 复位，再调 playRandomMusic() 和 startTipWindows()。注意它不清空 timeouts / wishElements——那是 closeAllWindows() 已经做过的事，重开时数组本来就是空的。若哪天允许「不收下全部就重开」，这里就得补一次清理，否则旧定时器会继续往场上加卡片。

十一、音乐：网易云在线歌单

loadPlaylist()（script.js:639）/ playRandomMusic()（script.js:662）（与博客左下角固定播放器用同一个歌单：网易云 9086662585，七百来首）

2026-11-07 起音乐不再存本地文件，改为在线播放。原理：

  • 页面打开时就 fetch 一次 Meting 中转（api.injahow.cn）拿歌单列表，约 199KB，和图片预加载并行，不挡任何事；loadPlaylist() 用”Promise 缓存”保证整个页面只请求一次，谁要结果都等同一个；
  • 点开始时从列表随机挑一首，把中转给的音频流地址塞给 <audio>，浏览器跟着 302 跳到网易云 CDN 边播边缓冲，不用等整首下完；随机时会避开上一首（lastTrackIdx）；
  • 一首播完或加载出错时自动换下一首（error 事件监听 script.js:845，最多重试 5 次，防止坏歌死循环）；单首仍然 loop 循环，行为和以前一致。

两个关键坑：

  • 自动播放限制：浏览器规定 play() 必须发生在用户点击的那一瞬间，而歌单是异步到达的。解法是点击瞬间先给 <audio> 塞一段静音音频（SILENT_WAV，unlockAudio()）播一下”解锁”播放器，歌单到了再换真歌就能响了。两个页面都这么干。
  • 中转站依赖：音乐走 api.injahow.cn 免费中转（实测国内可用）。它挂了音乐就不响，但不影响页面其他功能——fetch 失败只记日志。

为什么需要中转：网易云的直接外链（music.163.com/song/media/outer/url）已对匿名访问全面拦截（实测全部跳 404），hexo 圈通行的方案就是 Meting 中转——由中转服务器带着凭据去解析真实音频流。

歌单联动：往网易云歌单里加歌/删歌，网页里随机到的歌跟着变，不用重新部署。连连看页（source/link/script.js）用同一套逻辑和同一个歌单。

把「Promise 缓存」摊开看，这是全篇最值得记住的一个小模式（script.js:639）：

  • 第一行是全部机关：缓存的是那个 Promise 本身，不是结果。preloadAssets() 在页面加载时调一次、点开始时又调一次，第二次拿到的还是同一个 Promise，于是两个调用者一起等同一次网络请求，不会发两遍 199KB；
  • .filter(...) 把中转返回里没有 url 的条目剔掉，.map(...) 只留地址字符串。下游 playRandomMusic() 因此可以假定「数组里每一项都能直接塞给 audio.src」，不必各自判空；
  • .catch 里除了记日志，还把 playlistPromise 清空，这样下次调用会重新发起请求——中转偶尔抽风时能自愈。同时返回 [] 让调用方走「没有歌」的分支：页面照常弹卡片，只是没声音。外部依赖失败必须能降级，不能让主流程陪葬；
  • return [] 而不是 throw：错误已经在函数内部被消化了，调用方不需要写 try/catch，.then 里判断 !urls || !urls.length 即可。

unlockAudio() 为什么必须放在点击的同步调用栈里：fadeOutAndStart() 第一句就是 unlockAudio()，它给 <audio> 塞一段 base64 静音 wav 并立刻 play()。浏览器认的是「用户手势之后紧接着的播放动作」，一旦进了 setTimeout 或 .then，手势凭据就过期了。之后 playRandomMusic() 在 Promise 里换 src 再 play()，属于「已解锁的播放器换内容」，不再被拦。这也是为什么 500ms 的欢迎窗淡出要放在解锁之后。

playRandomMusic() 里 while (idx === lastTrackIdx) 避开上一首：歌单七百来首，撞车概率本来极低，但连续两首同一首歌会很明显，加一行就免了。注意 urls.length > 1 的判断——只有一首时这个 while 会死循环，别漏。

error 回调里 trackRetries >= 5 是重试上限：网易云有些歌因版权返回坏链，不设上限就会在坏歌之间无限打转并刷爆日志；满 5 次就安静下来，等用户手动点音乐按钮。这条和第八节「rainfall 两层 rAF」、第十节「isClosing 双保险」是同一类防御：把「理论上不会发生但一旦发生很难查」的情况用一行挡住。

十二、3D 背景：为什么用”动态 import”

script.js:730 mountBackground()

import() 是运行时才加载模块的写法，和顶部 import 的区别就是”用到才下载”。这里用它有三个原因：

  1. three.module.js 有 655KB，是全页最大的文件。用户还停在欢迎窗时不必下载，点了开始才拉取，首屏更快；
  2. 同一模块只会下载一次：第二次 import('./cake3d.js') 直接命中浏览器缓存（本页的”重新开启”就靠这个，秒重挂）；
  3. scene 参数一个文件出两种背景：生日季传 'cake' 出蛋糕，平时传 'star' 出星空，不用写两个文件。

cake3d.js 对外只暴露一个 mount(容器, 选项)，页面逻辑完全不知道里面 three.js 怎么用——渲染细节和页面逻辑隔离，以后换渲染引擎（比如换 CSS 动画）只动这一个文件。

把挂载函数摊开（script.js:730）：

  • bgMounted 在发起 import 之前就置真。import() 是异步的，若用户在这段等待里又触发一次调度（例如重开），没有这个标志就会挂两个 WebGL 画布、跑两套渲染循环，GPU 直接翻倍。布尔标志要放在异步操作之前，这是通用写法；
  • if (mod && mod.mount)：模块加载成功不代表导出了预期的函数，先探一下再调，避免版本不匹配时白屏；
  • cakeStage.classList.add('on') 只在 mount() 返回真值后加，样式靠这个 class 做淡入。意思是「渲染确实起来了才让容器可见」，否则用户会先看到一块空白矩形；
  • .catch 只记日志：3D 是装饰层，加载失败时 cakeStage 保持透明，页面原来的深蓝渐变背景还在，卡片、音乐、按钮全都不受影响。动态 import 的失败必须能吞掉，不能让它冒泡成未处理的 Promise rejection。

两次 import 的关系：第十四节 preloadAssets() 里有一句 import('./cake3d.js').catch(function(){})，那次是预热——只为了在用户还看欢迎窗时就把模块（和它依赖的 655KB three.js）拉进浏览器模块缓存，不调用任何导出。等 mountBackground() 再 import 时，浏览器按 URL 命中模块缓存，直接返回同一个模块对象，不产生第二次网络请求。所以「重新开启」几乎是瞬间的，不用重新下载引擎。这也是 ES 模块规范里「同一 URL 只求值一次」带来的免费收益。

为什么不用顶部静态 import：静态 import 会在 script.js 一执行就把整条模块图下载并执行完，首屏要等 655KB；而且传统 <script>（非 module）里根本写不了静态 import。动态 import() 可以在普通脚本里用，返回 Promise，正好配合「点了开始才挂载」的时机。代价是首帧会有一小段空窗，所以才配了预热那一行。

十三、3D 背景的算法（cake3d.js）

cake3d.js 全文约 1200 行，没有用任何外部模型/贴图文件——画面里所有东西都是代码算出来的点。拆成几块看：

13.1 一切皆是”点云”

主体用 three.js 的 Points 点云：每个形状是几千个带颜色的小点，点的外观是 canvas 现画的径向渐变贴图（圆点 sphereTexture、软光斑 softSprite、五角星 starSprite），一种形状一组缓冲 ≈ 1 次 draw call。两个例外：爆开的彩带是真网格（见 13.3），流星尾巴除了点还用一条 Line 连成连续光痕（见 13.4）。为什么不用实体模型：没有建模资源，一个 glTF 模型几百 KB 还得加载，点云只要代码，而且”星光颗粒”风格和页面的像素小窗风统一。

13.2 可复现随机数：mulberry32（cake3d.js:59）

每次挂载生成一个随机种子，用它派生出 3 条互不干扰的随机流（seed ^ 0x9E3779B9、seed ^ 0x85EBCA6B）：主流 rnd 同时供蛋糕几何和飘带/流星/星空这些环境粒子，brng 专门给爆开的 150 条彩带网格，crng 专门给彩纸。为什么：mulberry32 是可设种子的伪随机数生成器——同一个种子永远生成同一串”随机”数，画面可以完整复现（调试时改一个参数，其他都不变，才知道改动的效果）；分 3 条流是防止蛋糕多撒一个点、丝带就少一个随机数，两个系统互相”抢数”，牵一发动全身。

把生成器本身摊开（cake3d.js:59）：

  • seed >>> 0 把种子整理成 32 位无符号整数；a 是闭包里活着的状态，每调一次累加一个魔数再做几轮异或/乘法把位搅乱，最后除以 2³² 归一到 [0,1)。Math.imul 是 32 位整数乘法，避免普通 * 超过 2⁵³ 丢精度；
  • 为什么不用 Math.random()：它不能设种子，同一段代码每次刷新画面都不一样，调参数时根本分不清「是我改出来的效果」还是「这次随机换了一副」。可复现的伪随机数在图形调试里是刚需，和小游戏笔记里用固定种子复现牌局是同一个动机；
  • 三条流用 seed ^ 0x9E3779B9 这类不同魔数异或派生，得到的三个起始状态互相错开。注意它们不是「三份独立的随机数表」，而是同一个算法的三个不同起点；好处是只需记住一个种子就能复现整幅画面。

13.3 形状怎么变成点（采样算法）

  • 圆柱（sampleCylinder，cake3d.js:260）：68% 的点撒在侧面（半径 ±1.5% 抖动，让表面有绒感），32% 撒在顶面。顶面撒点用 √rnd × 半径——如果半径直接均匀随机，点会中间密边上稀；开平方后面积上均匀（半径 ∝ √面积）。三层圆柱叠出蛋糕的三层。
  • 椭球（sampleEllipsoid，cake3d.js:282）：装饰球、糖珠用。u∈[−1,1] 当 cosφ 定纬度，再取 k = ∛rnd（三次方根）缩放半径——体积均匀采样要求”半径 ∝ 三次方根”，和圆盘开平方是同一个道理的 3D 版。
  • 文字转点云（textPoints / extrudeText，cake3d.js:296）：倒计时数字 3、2、1 和 “Happy Birthday” 都不用字体文件——把白字画到黑底离屏 canvas 上 → 逐像素读亮度（红通道 >128 即笔画）→ 每隔 step 像素取一个点 → 换算成世界坐标；extrudeText 再给每个点随机 z 厚度变成 3D 字。零资源依赖，改字只改一个字符串。
  • 火焰（flame，cake3d.js:473）：每根蜡烛两层火焰（外橙 1400 点、内黄 1000 点）。半径随高度线性收缩到 0（火苗上尖下粗），点的高度 y = h × u^0.7 却偏向尖端——越细的地方点撒得越密，尖端才不会暗掉；运行时再按正弦缩放抖动（deform），看起来在摇。
  • 丝带网格（ribbonGeometry，cake3d.js:352）：爆炸彩带是真正的网格（不是点）：8 段窄条，边缘 x = 0.08 × sin(波数) 起波浪，每段两个三角形，双面材质。

13.4 粒子系统：一个套路”循环复用”

固定大小的 Float32Array 缓冲（点数永远不变，每帧零内存分配），粒子飞出活动盒就从另一侧重生：

  • 飘落丝带（makeRibbons，cake3d.js:919）：匀速下落 + sin 横摆，出底部回顶部；
  • 星空闪烁（makeStarfield，cake3d.js:1047）：整层透明度按 sin 呼吸，每层相位、频率不同 → 星星各自闪不齐步；x 方向还有极慢漂移；
  • 流星（makeMeteors，cake3d.js:961）：每条流星 = 头部亮点 + 沿运动反方向等距排的 16~18 个尾巴点，同一份坐标再叠一条 Line 把尾巴连成连续光痕；尾巴颜色从流星色向夜空色渐变（pow 0.55 曲线控制衰减快慢）；飞出边界就换随机方向重生；
  • 彩纸（confetti，500 个）：初始随机方向速度下落，出界回顶部。

13.6 固定 30 帧步进：动画速度和显示器刷新率解耦

cake3d.js:819 loop()：渲染按浏览器节奏（requestAnimationFrame，通常 60 次/秒），但逻辑 tick 用累加器驱动——攒够 1000/30 毫秒才跑一步，一次最多补 3 步。为什么：60Hz 和 144Hz 屏幕上动画快慢一致（逻辑按时间走，不按渲染帧数走）；机器卡顿时动画最多变慢，不会跳帧穿帮。

把累加器摊开（cake3d.js:819）：

  • acc 是时间欠账：这一帧距上一帧过了多少毫秒，就往里存多少；攒够一个 STEP（33.3ms）才跑一次 tick()，acc -= steps * STEP 把用掉的扣掉，余数留到下一帧。60Hz 屏大约每两帧跑一次逻辑，144Hz 大约每五帧一次，但每秒都恰好 30 次 tick；
  • Math.min(3, …) 是防死亡螺旋：页面被切到后台再回来，ts - prev 可能是好几秒，不封顶就会一帧内补跑几百次 tick，直接卡死；封顶后最多补 3 步，多余的时间被丢弃——动画「慢一点」比「卡住」好；
  • renderer.render() 在 for 之外，仍按浏览器刷新率每帧画一次。逻辑步进和画面刷新解耦，是游戏循环的标准写法。

13.7 鼠标交互的三个算法

  • 指针平滑（makePointer，cake3d.js:157）：当前值 += (目标值 − 当前值) × 0.08，指数趋近——鼠标猛甩，视角柔顺跟进，不抖。
  • 视差（parallax，cake3d.js:252）：先把相机的 right/up 基向量存下来（captureCam），然后让相机沿自己的右/上方向平移 0.45 个世界单位——移动的是相机不是场景，整个画面像在”转头看”。
  • 指针斥力（makeInteract，cake3d.js:191）：把每个注册过的点变换到世界坐标，算它到鼠标射线（不是屏幕上的一个点）的垂直距离，f = 1 − 距离/半径 线性衰减，按 f 把点沿垂直方向推开、颜色向白混 85%——星星会被鼠标”拨开发光”，松手弹回。

13.8 性能手段

  • 渲染分辨率封顶 1600px（makeResize，cake3d.js:42），devicePixelRatio 封顶 2——4K 屏也不会按物理像素渲染烧 GPU；
  • 点材质用 alphaTest 裁掉透明像素，而不是开真透明排序——省掉昂贵的深度排序；
  • frustumCulled = false：点云会整体移动/旋转，关掉视锥剔除防止整团星星突然消失的 bug；
  • 每帧只改 BufferAttribute 数组再标记 needsUpdate，不重建几何体——GC 压力为零。

四条性能手段各自在省什么：① 分辨率封顶省的是片元数量（4K 屏按物理像素渲染，像素数是 1080p 的四倍）；② alphaTest 省的是透明排序——真正半透明要按深度从后往前排几千个点，而点云是圆形贴图，直接把 alpha 低于阈值的像素丢弃即可，视觉一样、排序全省；③ frustumCulled = false 看着像「关掉优化」，其实是避开误判：整团点会旋转/移动，包围盒不准时会被整批剔除，画面突然一空；④ 每帧只改 Float32Array 再 needsUpdate = true，省的是对象分配与 GC——若每帧新建几何体，几秒后就会有一次可见的卡顿。四条分别对应 GPU 填充、CPU 排序、剔除正确性、内存分配，读性能代码时按这四类去找，比逐行看快得多。

十四、图片预加载

script.js:883 preloadAssets()

为什么必须预加载：站点托管在 GitHub Pages，从国内访问单个请求延迟很高（页面本身可能要 30 秒才打开）。原版逻辑是”卡片弹出那一刻才开始下载配图”，等于 21 张图各自排队等 GitHub 响应，卡片开出来图片区域长时间空白。

改法：页面一打开就把 21 张图（总共才 860K）全部下载进浏览器缓存。等用户看完欢迎窗、卡片开始弹的时候，图片早就在本地了，弹出即显示。代价是打开时多占一点带宽，换来整段观看期零等待——对慢网络是划算的交换。

new Image() 只设 src 不插进 DOM，是标准的”纯下载”手法：浏览器发现同一个 URL 已在缓存，卡片真正创建 <img> 时直接用缓存，不发第二个请求。

几个容易想岔的点：

  • 缓存的键是完整 URL。preloadAssets() 里写的是 'img/image' + i + '.jpg'，createRandomTipWindow() 里写的是一模一样的拼接（script.js:750），两处相对页面 /birthday/ 解析成同一个绝对地址，所以能命中。只要有一处多写个 ./ 或换了域名，浏览器就当成两个资源重新下载，预加载白做；
  • new Image() 创建的对象没被存进数组，循环一结束就没了引用。这没问题：请求由浏览器发起后会继续跑到完成，资源进的是 HTTP 缓存，不依赖这个 JS 对象是否存活。真正要留住的不是对象，是那个 URL 的缓存条目；
  • 21 张一共 860K，和 655KB 的 three.js、199KB 的歌单加起来是首屏约 1.7MB。这三样在 preloadAssets() 里同时发起，互不等待：图片靠 new Image()、歌单靠 fetch、引擎靠 import()，浏览器并行下载。若写成串行 await，总耗时就是三者相加；
  • import('./cake3d.js').catch(function(){}) 末尾那个空 catch 不能省：这只是预热，模块就算加载失败也不该影响主流程，而不带 catch 的动态 import 会抛一个未处理的 Promise rejection，控制台一片红。第十二节 mountBackground() 里那次才是真正使用，那里也有 catch，两处各管各的；
  • TOTAL_IMAGES = 21 和 img/ 里的文件数是手工约定：加一张图不改这个常量，第 22 张永远不会被预加载也不会被抽到；改大不改文件，会有一张图 404，靠 wishImage.onerror 兜底成纯文字卡片。第十六节速查表里把这两项放在一起，就是提醒它们要成对改。

  • fadeOutAndStart()：点开始后等 500ms（CSS 淡出动画的时长）再隐藏欢迎窗、起音乐、开卡片雨——动画时间和 JS 定时要对齐。

  • resize 监听（script.js:851）：缩放值和心形点重算，已弹出的卡片按 index % 新点数 重新摆放——窗口拖大拖小，心形跟着变但不乱。
  • applySeasonCopy()：平时身份的文案改造（标题、问候语、按钮文字），和生日判断集中在一处，改文案只动这里和文案池。问候语现在是两行——第一行 今天的小幸运已送达 🌿、第二行随机祝福 + ✨；🌿 和 ✨ 各自用 white-space: nowrap 的 <span> 包住，保证表情不会落单成行，但两行之间允许正常换行。

这五条看起来零散，其实都在处理同一类问题：浏览器和 JS 各自的时间线要对齐。

  • fadeInMainWindow() 的 100ms 是给浏览器「排完第一帧」留的。元素刚插入 DOM 时若同一帧里就加上 visible 类，浏览器会把初始态和最终态合并成一次样式计算，CSS transition 根本没有起点可补间，欢迎窗会直接闪现而不是淡入——第九节卡片要等 requestAnimationFrame 是同一个坑；
  • fadeOutAndStart() 的 500ms 必须等于 CSS 里 .fading-out 的动画时长。写短了欢迎窗还没淡完就被 display:none 掐掉，写长了会有一段「窗已淡没但还没藏」的空窗。这类数字最好在 CSS 和 JS 里各留一行注释互相指认，否则改样式的人不知道还有个 JS 常量跟着；
  • restartWishes() 不 location.reload()，是为了保住三样东西：已经缓存的 21 张图、已经求值过的 cake3d.js 模块、以及解锁过的 <audio>。刷新会把自动播放的用户手势凭据也清掉，音乐反而可能不响了；
  • resize 回调里 generateHeartPositions(heartPositions.length) 会重新随机选一种布局模式，所以拖窗口不只是缩放，心形的出现顺序也可能变。已弹出的卡片按 wishElements.forEach(function(el, i){ ... i % heartPositions.length ... }) 重新摆位，保持索引不变，卡片不会跳到无关的位置；没弹出的那些定时器仍按旧 delays 触发，但建卡时读的是新的 heartPositions，所以整体仍然对齐；
  • applySeasonCopy() 用 if (isBirthday) return 开头：生日季保留 index.html 里写死的原始文案，平时才改写。把「默认值」放在 HTML 里、把「例外」放在 JS 里，比两处都靠 JS 写更省，也让不看 JS 的人打开 HTML 就知道生日版长什么样。

三个状态标志也在这里收个尾：isClosing 管「别再建卡」（第十节）、bgMounted 管「别挂两次背景」（第十二节）、audioUnlocked 管「别重复播静音」（第十一节）。它们都是一次性开关：条件成立就再也不做第二次，而不是每次都要重新判断的开关。区分这两种布尔值，读别人的代码时会省很多力气。

自测

  1. 为什么整份 script.js 要包在 (function(){...})() 里，用 <script type="module"> 不是更现代？
    答：IIFE 在任何环境都能跑，包括用 file:// 双击打开的独立单页版；模块脚本受 CORS 限制，本地直接打开会被拦。它把几十个状态变量圈成私有变量，避免和主题脚本的全局变量撞名。代价是只能写 ES5 语法，于是循环里还得再套一层 IIFE 固定 idx。
  2. BIRTHDAY_MONTH = 7 是几月？判断为什么用两个 <= / >=？
    答：8 月，JS 的 getMonth() 从 0 数。闭区间让 20 号和 25 号都算进生日季，共 6 天；写成 < DAY_END 会少一天。判断结果只在开局算一次存进 isBirthday，页面开着跨零点也不会中途变身。
  3. 1280×800 的窗口会弹多少张卡？为什么不是按 1024000/16000 一直线性增长？
    答：48 张，恰好撞上 TIP_MAX。1920×1080 算出 130 也被夹回 48；手机 390×844 算出 21 会被 TIP_MIN 抬到 30。上限同时是视觉上限：点数再多，270 宽的卡片会重叠成一团，看不出心形。
  4. 心形为什么用参数方程，而不是把 30 多个点位写成常量表？
    答：卡片数按屏幕面积在 30~48 之间变，写死的表一换数量就得重摆；参数方程把 t 等分成 count 份就得到 count 个点，一个数量参数决定整颗心。代价是 t 等分不等于弧长等分，尖端会略密——卡片有宽度且允许重叠，这点误差看不见。
  5. delays 里存的到底是「间隔」还是「绝对时间」？把它当间隔用会怎样？
    答：绝对时间，直接交给 setTimeout。各模式用 delay += interval 累加生成，所以数组递增；若当成「相对上一张的间隔」去嵌套定时器，每张都要多等一次，节奏会越走越慢。delays = null 时退化的 idx * TIP_INTERVAL 同样是绝对时间。
  6. 卡片入场为什么非要等一次 requestAnimationFrame，直接加 visible 类不行吗？
    答：同一帧里既设初始态又设最终态，浏览器会合并成一次样式计算，transition 没有起点可补间，动画会被吞掉。rainfall 模式要两层，是因为它得先渲染「上方起始位置」那一帧，再把 top 改成目标值让 CSS 补间出落体。
  7. 已经 clearTimeout 了，为什么还要 isClosing？
    答：clearTimeout 只能取消还没到点的定时器，取消不了「已到点、正排在事件队列里」的回调。isClosing 在调度回调和建卡函数开头各挡一次，和清空 timeouts 数组一起堵住竞态，避免收下全部后还冒出「幽灵卡片」。
  8. 静音 wav 为什么必须放在点击的第一句，而不能等歌单加载完再一起播？
    答：浏览器把「用户手势」当作 play() 的许可凭据，凭据只在手势的同步调用栈里有效；进了 .then 或 setTimeout 就过期。unlockAudio() 先在点击瞬间解锁播放器，之后在 Promise 里换 src 属于「已解锁播放器换内容」，不再受限制。
  9. preloadAssets() 里已经 import 过 cake3d.js，mountBackground() 里为什么还 import 一次？
    答：前一次是预热，只把模块和 655KB 的 three.js 拉进缓存，不调任何导出；后一次才真正调 mount()。ES 模块按 URL 缓存，同一 URL 只求值一次，所以第二次不产生网络请求，「重新开启」才能瞬时重挂。两处都带 .catch，因为 3D 是装饰层，失败不能影响主流程。
  10. 3D 逻辑为什么按固定 30 帧走，而不是每次 requestAnimationFrame 都推进一帧？
    答：不同刷新率的屏幕 rAF 次数不同，按渲染帧推进会让 144Hz 上的动画快一倍多。累加器攒够 33.3ms 才跑一次 tick()，保证每秒恰好 30 步；Math.min(3, steps) 防止切后台回来一次补跑几百步卡死，宁可动画慢一点也不跳帧穿帮。
